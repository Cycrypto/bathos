# BATHOS — 토큰 & Quota 관리

> 멀티에이전트 파이프라인은 단일 대화보다 토큰이 훨씬 빨리 준다. 이 가이드는 **무엇이 비용을 만들고, 어떻게 통제하며, 한도에 걸렸을 때 어떻게 복구하는지**를 다룬다. 비싸게 배운 현장 교훈이 하나 깔려 있다: **팀원이 "멈춘 듯" 보이는 가장 흔한 원인은 버그가 아니라 계정 사용량 한도다.**
>
> **함께 보기:** [사용(USAGE-kr)](USAGE-kr.md) · [활용 사례(USECASE-kr)](USECASE-kr.md) · English: [`QUOTA-en.md`](QUOTA-en.md) · Español: [`QUOTA-es.md`](QUOTA-es.md)

## 0. 한 줄 요약

- **맞는 레벨을 골라라.** Scale-Adaptive Lv0–4가 가장 큰 비용 레버 — 버그 수정에 W0–W6를 돌리지 마라.
- **팀원 동시 ≤ 3.** 토큰 비용은 활성 역할 수에 대략 선형으로 비례한다; 엔진이 3으로 하드캡(`E-CONCURRENCY`).
- **필요한 역할만 스폰.** ML 없음 → Stephen 생략. 그린필드 → John 생략.
- **웨이브를 시퀀싱하라; 전부 병렬 금지.** 각 웨이브는 다음 전에 팀원을 shutdown.
- **멈추기 전 `/save`.** 웨이브 중 한도에 걸려도 디스크 산출물로 무손실 재개 — 리셋 후 웨이브만 재실행.
- **무출력으로 조용한 팀원은 대개 quota이지 크래시가 아니다.** 리셋 대기 후 재스폰.

## 1. 무엇이 비용을 유발하나

토큰이 새는 곳은 대략 넷이다:

| 유발 요인 | 왜 중요한가 | 레버 |
|-----------|-------------|------|
| **활성 팀원 수** | 스폰된 각 역할은 토큰을 쓰는 독립 에이전트; 비용은 활성 역할에 ~선형 | 동시 ≤ 3; 필요한 역할만 스폰 |
| **역할별 모델 티어** | Opus 역할이 Sonnet 역할보다 비쌈 | 빠듯하면 Sonnet 중심 웨이브부터 돌리고, Opus 역할은 집중 운용한다 |
| **실행 웨이브 수** | 웨이브가 많을수록 총 에이전트 작업량↑ | Scale-Adaptive 레벨(필요한 웨이브만) |
| **재게이트 사이클** | FAIL → 보완 → 재게이트 루프는 작업을 재실행 | W3 스토리 품질에 투자해 W5가 요동치지 않게 |

**역할 모델 맵**(누가 비싼가):
- **Opus 4.8:** Paul(리드), John, Caleb, Joshua, James, Jonnathan, Mark, Matthew(#17)
- **Sonnet 5:** Nathanael, Phillip, Andrew, Stephen, Timothy, Thomas, Michael, Hananiah, Matthias, Martin

즉 W2(Joshua→James, Jonnathan)와 W3(Matthew)는 Opus 밀도가 높고(설계 중심 — 깊이에 그만한 값어치가 있다), W5(Phillip/Andrew/Stephen)와 W6(Thomas/Timothy/Matthias→Martin)는 Sonnet 밀도가 높다.

## 2. 레버 #1 — Scale-Adaptive 레벨

웨이브를 덜 도는 게 가장 크게 아낀다. 대략의 규모는 이렇다:

| Lv | 도는 웨이브 | Opus 밀도 웨이브 | 상대 비용 |
|----|------------|------------------|:---------:|
| **0** | W5 (+초경량 W6) | 없음 | $ |
| **1** | 경량 W2 + W3(축약) + W5 + 경량 W6 | W2/W3(축약) | $$ |
| **2** | W1 + W2 + W3 + W5 + W6 | W2/W3 | $$$ |
| **3** | W0–W6 (W4 선택) | W0/W2/W3 | $$$$ |
| **4** | W0–W6 전체 + W4 | W0/W2/W3/W4 | $$$$$ |

**정직하게 규모를 맞춰라.** `/route`가 stakes로 레벨을 추천하지만 *당신이* 확정한다(User Sovereignty). "신규 제품"이 실은 집중 MVP라면 Lv2가 Lv3보다 나은 경우가 많다 — W0 시장분석과 W4 플러그를 건너뛴다. 나중에 언제든 상향 라우팅 가능.

---

## 3. 레버 #2 — 동시성 & 역할 선택

- **하드캡 3.** `MAX_CONCURRENT_ROLES = 3`; 웨이브에서 4번째 스폰은 `E-CONCURRENCY`로 거부. 맞서지 말고 존중하라.
- **작업이 필요한 역할만 스폰.** W5는 기본으로 Phillip/Andrew/Stephen을 스폰하지만:
  - 제품에 AI/ML 없음 → **Stephen 스폰 안 함**.
  - 그린필드 앱(리버스할 기존 코드베이스 없음) → W1에서 **John 생략**, 또는 참조 레포 1개만.
  - 백엔드 전용 변경 → Phillip만.
- **시퀀싱, 전부 병렬 금지.** 웨이브는 이미 순서대로 돌고 사이에 팀원을 shutdown한다. 웨이브 내부 순서도 존중(예: W2에서 Joshua 기획 게이트 후 James/Jonnathan 착수).

---

## 4. 레버 #3 — 선택 항목 연기

- **W4(IP·연구)는 본류 밖.** 토큰이 빠듯하면 본류(W0→W1→W2→W3→W5→W6)를 먼저 돌리고 W4는 나중에 — 이번 이터레이션엔 아예 생략해도 된다.
- **plan-review 게이트는 선택.** `/plan-ceo-review`, `/plan-eng-review` 등은 Opus 리뷰 패스를 추가한다. 고위험 기획엔 쓰고, 작은 건 생략.

## 5. 사용량 한도 도달 — 인식 & 복구

**알아채라.** 스폰한 팀원이 **아무 출력 없이 "멈춘 듯"** 보이면, 열에 아홉은 코드나 훅 버그가 아니라 **계정 사용량(session) 한도**다. 한도에 걸린 팀원은 추론을 못 해 프로세스만 살아 있는 채 조용해지는데, 겉보기엔 hang과 똑같다. (해당 팀원의 트랜스크립트에 "you've hit your session limit / resets at …" 메시지가 남는다.)

**복구 — 무손실.** BATHOS는 **모든 인수인계가 디스크에 있고**(`.agent-team/`) 팀원이 인메모리 대화 히스토리에 의존하지 않으므로 이에 대비돼 있다:

1. **함부로 kill 하지 마라.** 한도에 걸린 조용한 팀원은 고장난 게 아니라 대기 중이다.
2. **`/save`**(리드가 아직 동작 가능하면)로 세션 스냅샷.
3. **quota 리셋 대기.**
4. **재스폰:** 해당 `/waveN-…` 커맨드 재실행. 상류 산출물이 디스크에 있으므로 재스폰된 팀원이 정확히 그 지점부터 이어받는다 — 작업 손실 0.

> 이것이 `/save`+`/resume`과 디스크 전용 인수인계가 중요한 이유다: 사용량 한도가 손실이 아니라 일시정지가 된다.

---

## 6. 실전 저-quota 플레이북

토큰을 아끼며 집중 빌드할 때:

1. `/route` → 맞는 **가장 낮은** 레벨 확정(대개 Lv1–Lv2).
2. 웨이브를 **하나씩** 돌리고 사이에 `/team-status` 확인.
3. 각 웨이브에서 **필요한 역할만** 스폰(무관하면 Stephen/John 생략).
4. **W4와 무거운 plan-review 연기.**
5. 각 세션 끝(및 긴 웨이브 전)에 **`/save`**.
6. 팀원이 조용해지면: quota로 가정, `/save`, 리셋 대기, `/resume` + 웨이브 재실행.
7. quota가 넉넉할 때(리셋 직후) Opus 밀도 웨이브(W2/W3)를 우선 실행한다.
